Hilfe: Einrichtung und Bedienung

Alles für die Inbetriebnahme auf einer Seite: Zugänge, Konfiguration, Befehle, Menüs. Ausführlich in README.md, EINRICHTUNG.md und BETRIEB.md im Projektordner.

Ablauf in sechs Schritten

1. InstallierenPython 3.10+, Projekt kopieren, .venv anlegen, Selbsttest.
2. Apple-ZugangTeam-Schlüssel (.p8), Issuer ID, Key ID, App-IDs, Analytics-Berichtsanfrage.
3. Google-ZugangNur bei Android: Service Account (JSON), in Play Console einladen, Paketnamen.
4. Konfigurierenconfig/config.json: Kunden, Zugangsdaten, Apps. Schlüssel nach keys/.
5. Prüfen./ratings.sh apps, dry-run, dann fetch, stability, store, testdata, report.
6. AutomatisierenTäglich ./ratings.sh daily per cron oder systemd; Bericht bereitstellen; Backup.

Voraussetzungen und Installation

  • System: Linux (empfohlen), macOS oder Windows. Python 3.10 oder neuer, dazu venv und pip. Einzige Abhängigkeit: cryptography. Keine Datenbank, kein Server.
  • Netz: ausgehendes HTTPS zu api.appstoreconnect.apple.com, itunes.apple.com, androidpublisher.googleapis.com, oauth2.googleapis.com, playdeveloperreporting.googleapis.com und Apples Download-Hosts für Analytics-Berichte. Kein eingehender Port. Proxy über HTTPS_PROXY.
  • Zeitplaner: cron oder systemd-Timer. Ein täglicher Lauf ist Pflicht, weil Google nur sieben Tage rückwirkend liefert.
git clone <repo-url> ~/app-ratings-reviews      # oder Ordner kopieren (ohne data/, reports/, config.json)
cd ~/app-ratings-reviews
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
cp config/config.example.json config/config.json
mkdir -p keys && chmod 700 keys && chmod 600 config/config.json
./ratings.sh test                                  # Selbsttest, installiert pytest beim ersten Mal

ratings.sh, menu.sh und kurzmenu.sh richten das .venv beim ersten Start selbst ein; ein manuelles source ist nicht nötig. Auf einem Server das Projekt unter einem eigenen Benutzer (z. B. ratings) ablegen.

Apple: App Store Connect einrichten

Was beantragt werden muss (je Entwicklerkonto)

  1. App Store Connect → Benutzer und Zugriff → Integrationen → App Store Connect API → Team-Schlüssel erzeugen. Kein „Individual Key“. Das darf nur der Account-Inhaber oder ein Admin.
  2. Rolle: „App-Manager“ (nötig für Stabilität und TestFlight). Nur für Rezensionen reicht „Kundensupport“.
  3. Herunterladen und übergeben: die Datei AuthKey_<KeyID>.p8 (nur einmal herunterladbar!), die Issuer ID und die Key ID.
  4. Für Stabilitätsdaten je App einmalig eine Analytics-Berichtsanfrage mit Zugriffsart ONGOING in App Store Connect anlegen. Daten gibt es erst ab diesem Zeitpunkt.
  5. Die numerischen App-IDs notieren (App Store Connect → App → App-Informationen → Apple-ID, oder aus der Store-URL id1234567890).

So sehen die Zugangsdaten aus

WertFormWo in der Konfiguration
Issuer IDUUID, z. B. 11111111-2222-3333-4444-555555555555credentials.apple.issuerId
Key ID10 Zeichen, z. B. ABC123DEFG, steht im Dateinamen der .p8credentials.apple.keyId
Privater SchlüsselDatei AuthKey_ABC123DEFG.p8 (Text, beginnt mit -----BEGIN PRIVATE KEY-----)credentials.apple.privateKeyFile (Pfad) oder privateKeyEnvironmentVariable (Name einer Umgebungsvariable mit Pfad oder Schlüsseltext)
App-IDZahl, z. B. 1234567890apps[].platforms.apple.appId

Aus Issuer ID, Key ID und Schlüssel erzeugt das Programm selbst ein kurzlebiges Token (ES256, 15 Minuten). Es muss nichts von Hand erzeugt werden. Alle Aufrufe sind nur lesend. Der Schlüsseltext darf nie in config.json stehen; das Programm lehnt das ab.

Google: Play Console einrichten (nur bei Android-Apps)

  1. In einem eigenen Google-Cloud-Projekt (eines reicht für alle Kunden) einen Service Account anlegen und einen JSON-Schlüssel erzeugen.
  2. APIs aktivieren: Google Play Android Developer API; für Absturzraten zusätzlich Google Play Developer Reporting API.
  3. Der Inhaber der Play Console lädt die E-Mail-Adresse des Service Accounts ein (Nutzer und Berechtigungen) mit den Rechten: „App-Informationen anzeigen (nur lesend)“, „Rezensionen anzeigen“, optional „Statistiken zur App-Qualität“. Wirkung bis zu 48 Stunden verzögert.
  4. Die Paketnamen notieren (z. B. de.firma.app, aus der Play-Store-URL id=…).
WertFormWo in der Konfiguration
Service-Account-SchlüsselJSON-Datei mit client_email, private_key, token_uricredentials.google.serviceAccountFile (Pfad) oder serviceAccountEnvironmentVariable
Paketnamez. B. de.firma.appapps[].platforms.google.packageName

Keine Android-Apps: bei der Plattform "enabled": false setzen oder den Eintrag weglassen. Google liefert nur Rezensionen der letzten sieben Tage; ältere Daten über ./ratings.sh import-csv aus einem Play-Console-Export. Die Google-Anbindung ist implementiert, aber noch nicht im Betrieb geprüft.

Konfiguration: config/config.json

Ein Kunde = ein Eintrag in customers mit eigenen Zugangsdaten und seiner App-Liste. Die id wird zum Ordnernamen unter data/customers/ und darf später nicht mehr geändert werden (Buchstaben, Ziffern, . _ -).

{
  "schemaVersion": 1,
  "settings": { "minRefreshMinutes": 30, "fullSyncIntervalDays": 30, "overlapDays": 7, "logLevel": "INFO" },
  "customers": [
    {
      "id": "kunde-a", "name": "Kunde A", "enabled": true,
      "credentials": {
        "apple":  { "issuerId": "11111111-2222-3333-4444-555555555555", "keyId": "ABC123DEFG", "privateKeyFile": "./keys/kunde-a.p8" },
        "google": { "serviceAccountFile": "./keys/kunde-a-google.json" }
      },
      "apps": [
        { "id": "meine-app", "name": "Meine App", "enabled": true, "audience": 250000, "platforms": {
            "apple":  { "enabled": true, "appId": "1234567890", "countries": [], "ratingCountries": ["DE"] },
            "google": { "enabled": false, "packageName": "de.firma.app", "languages": [] } } }
      ]
    }
  ]
}
  • Je Kunde eigene credentials, weil Apple-Schlüssel an das Entwicklerkonto gebunden sind. Mehrere Kunden unter einem Konto: denselben Schlüssel bei jedem eintragen. Ein Google-Service-Account kann in mehrere Play Consoles eingeladen werden.
  • ratingCountries: Länder, für die die offizielle Store-Note geholt wird (eine Anfrage je App und Land pro Lauf; [] = aus). countries bei Apple und languages bei Google leer lassen (alle).
  • audience (optional): Größe der Zielgruppe der App, etwa die Zahl der Kunden des Anbieters. Nur damit zeigt der Bericht „Downloads je 1000 der Zielgruppe“; ohne Angabe bleibt die Spalte leer.
  • competitors (optional, je Kunde): fremde Apple-Apps, die neben den eigenen ausgewertet werden, ohne Zugang: je Eintrag id, name, optional vendor, dazu apple.appId (aus dem App-Store-Link) und apple.countries (Pflicht, z. B. ["DE"]). Quelle: öffentlicher Apple-Feed (jüngste 500 Rezensionen je Land) und iTunes Lookup. Nur Apple; für Google gibt es keine öffentliche Quelle. Ohne Einträge erscheint im Bericht nichts dazu; mit Einträgen gibt es den Reiter „Wettbewerber“ und die Einträge im App-Filter mit Präfix „Wettbewerber:“.
  • config/themen.json (versioniert, keine Geheimnisse): Wortlisten für den Bereich „Themen und Wörter“ im Bericht. Je Thema id, Name de/en, Art (problem, wunsch, lob, bedienung, thema), optional bereich (app oder anbieter, für die Frage „Liegt es an der App oder am Anbieter?“) und terms (Begriffe in Kleinschreibung; Treffer am Wortanfang, bis drei Zeichen nur als ganzes Wort, * davor auch mitten im Wort, = davor nur das ganze Wort) sowie optional nicht (Phrasen, in denen ein Treffer nicht zählt, etwa „keine Fehler“). Neue Begriffe einfach ergänzen und den Bericht neu erzeugen; die Zuordnung läuft im Browser, ohne API-Aufruf.
  • Umgebungsvariablen statt Dateien: privateKeyEnvironmentVariable bzw. serviceAccountEnvironmentVariable nennen den Namen der Variable (Inhalt: Pfad oder Schlüsseltext). Praktisch für CI.

Das Programm selbst erzeugt data/ (Rezensionen als JSON, bleibt dauerhaft), reports/index.html (Bericht), reports/hilfe.html, impressum.html, datenschutz.html (diese Seiten), reports/markdown/ (Zusammenfassungen) und backups/ (vor dem Löschen). Nichts davon ist im Repository. Es wird nie etwas gelöscht, außer bewusst über ./ratings.sh reset mit Backup und Bestätigung LOESCHEN.

Empfohlene Reihenfolge beim ersten Mal

./ratings.sh apps                      # alle Kunden und Apps gelistet?
./ratings.sh dry-run                   # alle Zugänge prüfen, nichts speichern
./ratings.sh fetch                     # erster Abruf der Rezensionen
./ratings.sh stability                 # Apple Analytics (dauert beim ersten Mal)
./ratings.sh testdata                  # TestFlight-Builds (eine Anfrage je Build)
./ratings.sh report                    # Bericht erzeugen und öffnen
./ratings.sh status                    # je App: ok, teilweise oder Fehler

Exit-Codes: 0 alles in Ordnung, 1 mindestens ein Ziel fehlgeschlagen oder teilweise, 2 Konfigurations- oder Aufruffehler. Direkt ohne Hülle: python collect.py [Optionen] und python report.py [--customer ID] [--app ID] [--platform P].

Der Bericht

Eine einzige HTML-Datei (reports/index.html), die offline funktioniert. Oben steht der Filter (Kunde, App, Plattform, Zeitraum, Freitextsuche; „Erweitert“ mit Sprache, Land, Version, Betriebssystem, Gerät, Thema, Sternen, Entwicklerantwort, Von/Bis), alles darunter folgt ihm. Klick auf „App-Feedback“ oben links führt zum Überblick an den Seitenanfang. Sprache (DE/EN) und Hell/Dunkel oben rechts; jeder Bereich hat ein rotes i mit Erklärung und einen Pfeil zum Zuklappen.

ReiterInhalt
Überblickdrei Antworten (wie läuft es, was ist auffällig, was hat das letzte Update verändert), „Das sollten wir tun“ (mit KI), Ampel je App; „Mehr Zahlen anzeigen“ öffnet Fragen und Antworten, die wichtigsten Zahlen je App, Vergleich nach Version und alle Updates
RezensionenDurchschnitt aus den Rezensionen, Kennzahlen, „Themen und Wörter“ (mit KI drei Knöpfe als Overlay), die Rezensionen selbst mit Detailansicht, „Antworten des Supports“ (mit KI Antwortentwürfe)
StabilitätAbstürze und Sitzungen nach Version, System, Gerät, Wochenverlauf (nur Apple)
Downloads & StoreApps im Vergleich (mit App-Bericht zum Drucken), Sterne im App Store, neueste Version im Store
Diagrammeneunzehn Diagramme, Auswahlbox, Pfeile, Vergrößern
Wettbewerbernur mit eingetragenen Wettbewerbern (siehe unten)
KI-Anfragennur bei laufendem Fragedienst: Frage eingeben oder aus 20 vorbereiteten wählen, gespeicherte Antworten mit Belegen
Datenstandwie vollständig die Daten sind: Grenzen der Quellen, letzter Abruf je App, Lücken

Drucken und Zwischenablage

  • Je Reiter: Oben in der Karte (Überblick, Themen und Wörter, Stabilität, Downloads & Store, Diagramme) stehen „Bericht drucken“ (im Überblick „Monatsbericht drucken“: letzte 30 Tage mit Lage, Ampel, Maßnahmen, mit KI die Stimmen der Nutzer) und „In Zwischenablage“. Der Themen-Bericht enthält Gesamtbewertung, Kennzahlen und die Themen für alle und für negative Rezensionen (mit KI die meistgewünschten Funktionen); der Diagramm-Bericht zehn Diagramme, bei fehlender Plattform mit „Nur für iOS/Android“.
  • Gesamtbericht: „Bericht drucken“ und „In Zwischenablage“ neben „Filter zurücksetzen“ geben alle verfügbaren Berichte nach Reitern gruppiert aus. Liegen KI-Fragen vor, fragt der Bericht vorher, ob sie mit hinein sollen; „Nein“ lässt den Block weg.
  • Jeder Ausdruck beginnt mit Datum und Uhrzeit und dem eingestellten Filter. Im Druckdialog „Als PDF sichern“: Der Dateiname ist vorgeschlagen, etwa Monatsbericht-BKK-Linden-20261025-233856. Ohne KI enthält kein Ausdruck KI-Texte.
  • Zwischenablage: derselbe Bericht mit Formatierung, Diagramme als Bilder, zum Einfügen in Word, Outlook, Teams oder Jira (in Jira und Teams hängt die Bildübernahme vom Editor ab). Bei jeder KI-Frage kopiert der Knopf neben „Löschen“ Frage, Antwort und Belege als Text.
  • Zurücksetzen (rechts daneben) leert nach Rückfrage den Filter und löscht alle gespeicherten KI-Anfragen; auf der Platte nur bei laufendem Fragedienst, sonst erscheint ein Hinweis.

KI-Analyse (optional)

Zusätzlich zu den Zahlen kann ein Sprachmodell die Rezensionen lesen: Zusammenfassung je App in drei Sätzen mit Zitaten als Beleg, Stimmung und Dringlichkeit je Rezension (auch wo die Sterne täuschen), frei erkannte Themen mit Vorschlägen für config/themen.json, Häufungen nach Version, Vergleich der Apps, Antwortentwürfe für offene 1–2-★-Rezensionen und Freitextfragen. Dazu eine Maßnahmenliste je App (Zuständigkeit, Wirkung, Anteil der betroffenen negativen Rezensionen), die meistgewünschten Funktionen und eine Wirkungskontrolle je Update. Es gibt keinen eigenen KI-Reiter: Jeder KI-Text steht in dem Bereich, der die Frage beantwortet (Überblick „Das sollten wir tun“ und „Was sagen die Nutzer?“, Reiter Rezensionen, „Themen und Wörter“, „Antworten des Supports“, „Apps im Vergleich“, „Was ein Update verändert hat“); nur „Fragen an die Daten“ hat einen eigenen Reiter „KI-Anfragen“.

Einschalten: In config/config.json den Block ai aus config.example.json übernehmen. Die KI ist nur aktiv, wenn ein Anbieter in ai.providers "enabled": true hat und die in apiKeyEnvironmentVariable genannte Umgebungsvariable einen Schlüssel enthält (zum Beispiel export ANTHROPIC_API_KEY=…). Sind mehrere freigeschaltet, zählt der erste in der Liste; wechseln heißt Reihenfolge ändern oder enabled umstellen. Anbieter: openai, gemini, anthropic, perplexity, xai (Cloud) oder local (lokales Modell auf dem eigenen Rechner, ohne Schlüssel und kostenlos, z. B. Ollama oder LM Studio; bei Ollama installieren, ollama pull llama3.1:8b, Anbieter einschalten; Einrichtung und Modellwahl in KI.md); das Modell je Anbieter ist frei wählbar (model). Ohne aktiven Anbieter gibt es weder den Befehl noch KI-Inhalte im Bericht.

Kosten: Es werden nur neue oder geänderte Rezensionen gesendet. monthlyTokenLimit ist eine harte Bremse je Kalendermonat; ./ratings.sh ai-usage zeigt den Verbrauch. Freitextfragen (ai.features.questions) sind standardmäßig aus, weil jede Frage eine Anfrage kostet. Preise stehen beim Anbieter; das Programm speichert keine.

Datenschutz: Gesendet werden Rezensionstext und Titel (abschaltbar: sendReviewText: false), Sterne, Datum, App-Version, Sprache, Land und App-Name; nie Nutzernamen, Rezensions-IDs, Zugangsdaten oder Store-Kennzahlen. Jede KI-Aussage trägt die Marke „KI“ und nennt Anbieter, Modell und Datum. Zitate werden gegen den Originaltext geprüft; Antwortentwürfe werden nie gesendet, nur zum Kopieren angezeigt. Details in der Datenschutzerklärung, Abschnitt 4a.

Fragen direkt im Bericht: ./ratings.sh ai-report erledigt alles in einem Schritt: Dienst starten, Bericht erzeugen, Browser öffnen. Dahinter steckt ./ratings.sh ai-serve, das einen kleinen Dienst, der nur auf diesem Rechner (127.0.0.1) erreichbar ist. Wird der Bericht erzeugt, während er läuft, erscheint im Reiter „KI-Anfragen“ ein Eingabefeld, daneben „Fragen wählen …“ mit 20 vorgefertigten Fragen aus config/fragen.json (frei änderbar; ein Klick stellt die Frage sofort); der Bericht darf dann genau diesen Port ansprechen, sonst macht er keine Netzanfragen. Schutz: zufälliges Token je Start, nur erlaubte Browser-Herkunft, Anfragen auf 4 KB begrenzt, dasselbe Budget wie sonst. Strg+C beendet den Dienst; der auf dem Server bereitgestellte Bericht kann keine Fragen stellen.

./ratings.sh analyze                   # alle Apps, nur Neues wird gesendet
./ratings.sh analyze --dry-run         # zeigt nur, was gesendet würde
./ratings.sh ask "Welche Apps erwähnen das Bonusprogramm?" --customer kasse-nord
./ratings.sh ai-themes                 # Vorschläge nummeriert; --accept 2 übernimmt, --ignore 2 lehnt ab
./ratings.sh ai-usage                  # Anbieter, Begründung je Anbieter, Tokens je Monat
./ratings.sh ai-questions              # gespeicherte Fragen; --delete NR oder --clear löscht
./ratings.sh ai-models                 # unterstützte Modelle je Anbieter mit Listenpreisen

Im Bericht: Alle KI-Texte tragen die Marke „KI“. Sie stehen im Überblick („Das sollten wir tun“, „Was sagen die Nutzer?“), bei den Rezensionen (Stimmungsleiste, Kacheln, drei Knöpfe unter „Themen und Wörter“, Antwortentwürfe), bei „Apps im Vergleich“ und „Was ein Update verändert hat“ sowie im Reiter „KI-Anfragen“. In den Ausdrucken erscheinen sie nur mit eingeschalteter KI; der Gesamtbericht fragt vorher, ob die gespeicherten KI-Anfragen mit hinein sollen. Menü: Hauptmenü Punkt 9 (KI-Analyse) und Punkt 5 (Bericht mit Fragedienst), Kurzmenü Punkt 4.

Wettbewerber (optional, nur Apple)

Fremde Apple-Apps lassen sich neben den eigenen auswerten, ohne Zugang: Das Programm liest den öffentlichen Apple-Feed (neueste 500 Rezensionen je Land) und den iTunes Lookup (Store-Note, Bewertungen gesamt, Version). Für Google gibt es keinen öffentlichen Weg.

  • Einrichten: in config/config.json je Kunde den Block competitors (Vorlage in config.example.json): je Eintrag id, name, optional vendor, dazu apple.appId aus dem App-Store-Link und die Länder. Ohne Einträge ändert sich am Bericht nichts.
  • Abrufen: ./ratings.sh competitors, in all und daily enthalten; Menü: Daten abrufen → Wettbewerber.
  • Im Bericht: eigener Reiter „Wettbewerber“ mit Tabelle (Hersteller, Store-Note, Bewertungen gesamt, Rezensionen der letzten 90 Tage, Ampel nach denselben Regeln) und Steckbrief je App; mit KI, was die Nutzer loben und bemängeln. Der Reiter folgt dem Kunden im Filter. Wettbewerber zählen sonst nirgends mit: nicht im Überblick, nicht in den Ausdrucken, nicht in der Benachrichtigung.
  • Datenschutz: gespeichert werden nur Rezensionstexte und Kennzahlen aus dem öffentlichen Feed, keine Nutzernamen; mit KI gehen auch diese Texte an den Anbieter.

Die zwei Menüs

Beide starten von jedem Ordner aus, richten das .venv beim ersten Mal ein und melden eine fehlende config.json. Tasten: Zahl = Auswahl, H = Hilfe zum jeweiligen Menü, 0 = eine Ebene zurück, Q = beenden. Oben stehen der letzte erfolgreiche Abruf, das Alter des Berichts und die aktuelle Auswahl. Jeder Befehl wird vor dem Start angezeigt; nach einer Ausgabe wartet das Menü auf Enter.

Großes Menü: menu.sh (oder ./ratings.sh menu)

Täglicher Lauf, Bereitstellung, Backup

  • Zeitplan: ./ratings.sh daily einmal täglich (Abruf, Bericht, zuletzt die Benachrichtigung). cron: 30 6 * * * cd /home/ratings/app-ratings-reviews && ./ratings.sh daily >> logs-daily.txt 2>&1. Fertige systemd-Units und die Varianten Mac, Windows und GitHub Actions stehen in BETRIEB.md.
  • Bereitstellung: reports/ ist statisch und ohne externe Abhängigkeiten. Per Webserver mit Passwort oder VPN freigeben, oder den Ordner auf ein Netzlaufwerk legen (reportDirectory). Nur reports/ freigeben, nie config/, data/ oder keys/.
  • Versand: ./ratings.sh markdown erzeugt je App eine Zusammenfassung der letzten 14 Tage und ein ZIP.
  • Backup: ./ratings.sh backup packt data/; zusätzlich config/ und keys/ in die Serversicherung aufnehmen.
  • Verantwortung: jemand sieht bei Status „Fehler“ im Log nach; meist ist ein Schlüssel widerrufen oder abgelaufen.

Benachrichtigung (optional)

Damit niemand den Bericht täglich öffnen muss: Am Ende von ./ratings.sh daily schickt das Programm eine knappe Nachricht per E-Mail, Slack oder Webhook, aber nur, wenn seit der letzten Nachricht etwas passiert ist. Nichts Neues, keine Nachricht.

  • Auslöser: neue Rezensionen mit ein oder zwei Sternen (mit Kurzsatz der KI, falls die Analyse läuft), Ampelwechsel einer App (gelb, rot oder zurück auf grün, mit den Gründen wie im Bericht), Sprung der Absturzrate. Jeder einzeln abschaltbar (notify.triggers).
  • Einschalten: Block notify in config/config.json (Vorlage in config.example.json), enabled: true und beim Kanal ebenfalls; settings.reportUrl liefert den Link in der Nachricht. Passwort, Webhook-Adresse und Signaturschlüssel nur als Umgebungsvariablen des Zeitplaners, nie in der Datei.
  • Kanäle: E-Mail über SMTP (STARTTLS oder SSL), Slack Incoming Webhook, generischer Webhook (JSON per POST, optional signiert mit X-Ratings-Signature). Alle freigeschalteten Kanäle werden bedient.
  • Verhalten: Der erste Lauf meldet nichts, er merkt sich nur den Stand (data/notify-state.json). Jeder Vorfall wird nur einmal gemeldet, auch wenn daily mehrmals läuft. Kann kein Kanal zustellen, meldet der nächste Lauf dieselben Vorfälle erneut.
  • Prüfen: ./ratings.sh notify --test schickt eine Testnachricht an alle Kanäle; ./ratings.sh notify --dry-run zeigt, was der nächste Lauf melden würde (Menü: Status und Übersicht → Benachrichtigung ansehen oder testen). Beides auch im Menü unter „Status und Übersicht“.
  • Datenschutz: Die Nachricht enthält Rezensionsauszüge (Sterne, Datum, Land, Titel, Text gekürzt); die Empfänger gehören in die Firma. Nutzernamen kommen nicht vor. Für die KI-Sätze wird keine neue Anfrage gestellt. Alles Weitere steht in BENACHRICHTIGUNG.md.

Requirements and installation

  • System: Linux (recommended), macOS or Windows. Python 3.10 or newer with venv and pip. Only dependency: cryptography. No database, no server.
  • Network: outbound HTTPS to api.appstoreconnect.apple.com, itunes.apple.com, androidpublisher.googleapis.com, oauth2.googleapis.com, playdeveloperreporting.googleapis.com and Apple’s download hosts for analytics reports. No inbound port. Proxy via HTTPS_PROXY.
  • Scheduler: cron or a systemd timer. A daily run is mandatory because Google only returns the last seven days.

Apple: setting up App Store Connect

What to request (per developer account)

  1. App Store Connect → Users and Access → Integrations → App Store Connect API → generate a Team key. Not an “Individual Key”. Only the Account Holder or an Admin can do this.
  2. Role: “App Manager” (required for stability and TestFlight). For reviews alone, “Customer Support” is enough.
  3. Download and hand over: the file AuthKey_<KeyID>.p8 (can only be downloaded once!), the Issuer ID and the Key ID.
  4. For stability data, create one analytics report request per app with access type ONGOING in App Store Connect. Data exists only from that moment on.
  5. Note the numeric app IDs (App Store Connect → App → App Information → Apple ID, or from the store URL id1234567890).

What the credentials look like

ValueFormWhere in the configuration
Issuer IDUUID, e.g. 11111111-2222-3333-4444-555555555555credentials.apple.issuerId
Key ID10 characters, e.g. ABC123DEFG, part of the .p8 file namecredentials.apple.keyId
Private keyFile AuthKey_ABC123DEFG.p8 (text, starts with -----BEGIN PRIVATE KEY-----)credentials.apple.privateKeyFile (path) or privateKeyEnvironmentVariable (name of an environment variable holding a path or the key text)

The tool creates a short-lived token itself from Issuer ID, Key ID and key (ES256, 15 minutes). Nothing has to be generated by hand. All calls are read-only. The key text must never be placed in config.json; the tool rejects that.

Google: setting up the Play Console (Android apps only)

  1. In your own Google Cloud project (one is enough for all customers) create a service account and generate a JSON key.
  2. Enable the APIs: Google Play Android Developer API; for crash rates also Google Play Developer Reporting API.
  3. The Play Console owner invites the service account’s e-mail address (Users and permissions) with: “View app information (read-only)”, “View reviews”, optionally “View app quality statistics”. Takes effect after up to 48 hours.
  4. Note the package names (e.g. de.firma.app, from the Play Store URL id=…).

No Android apps: set "enabled": false for the platform or omit the entry. Google returns only reviews from the last seven days; older data via ./ratings.sh import-csv from a Play Console export. The Google integration is implemented but not yet verified in production.

Configuration: config/config.json

One customer = one entry in customers with its own credentials and app list. The id becomes the folder name under data/customers/ and must not be changed later (letters, digits, . _ -).

{

  "settings": { "minRefreshMinutes": 30, "fullSyncIntervalDays": 30, "overlapDays": 7, "logLevel": "INFO" },
  "customers": [
    {
      "id": "customer-a", "name": "Customer A", "enabled": true,
      "credentials": {
        "apple":  { "issuerId": "11111111-2222-3333-4444-555555555555", "keyId": "ABC123DEFG", "privateKeyFile": "./keys/customer-a.p8" },
        "google": { "serviceAccountFile": "./keys/customer-a-google.json" }
      },
      "apps": [
        { "id": "my-app", "name": "My App", "enabled": true, "audience": 250000, "platforms": {
            "apple":  { "enabled": true, "appId": "1234567890", "countries": [], "ratingCountries": ["DE"] },
            "google": { "enabled": false, "packageName": "de.firma.app", "languages": [] } } }
      ]
    }
  ]
}
  • Separate credentials per customer, because Apple keys are bound to the developer account. Several customers under one account: enter the same key for each. One Google service account can be invited to several Play Consoles.
  • ratingCountries: countries for which the official store rating is fetched (one request per app and country per run; [] = off). Leave countries (Apple) and languages (Google) empty for all.
  • audience (optional): size of the app’s target group, for example the provider’s number of customers. Only with it does the report show “downloads per 1,000 of target group”; without it the column stays empty.
  • competitors (optional, per customer): third-party Apple apps analysed next to your own, without credentials: per entry id, name, optional vendor, plus apple.appId (from the App Store link) and apple.countries (required, e.g. ["DE"]). Source: Apple’s public review feed (newest 500 reviews per country) and iTunes Lookup. Apple only; Google offers no public source. Without entries nothing about it appears in the report; with entries there is a “Competitors” tab and the app filter lists them with the prefix “Competitor:”.
  • config/themen.json (versioned, no secrets): word lists for the “Topics and words” section of the report. Per topic id, name de/en, kind (problem, wunsch, lob, bedienung, thema), optional bereich (app or anbieter, for the question “Is it the app or the provider?”) and terms (lower-case terms; matched at the start of a word, up to three characters only as a whole word, * in front also inside a word, = in front only as a whole word) plus optional nicht (phrases in which a hit does not count, such as “keine Fehler”). Add terms and rebuild the report; matching runs in the browser without any API call.
  • Environment variables instead of files: privateKeyEnvironmentVariable and serviceAccountEnvironmentVariable name the variable (content: path or key text). Handy for CI.

AI analysis (optional)

In addition to the figures, a language model can read the reviews: a three-sentence summary per app with quotes as evidence, sentiment and urgency per review (including where the stars mislead), freely detected topics with suggestions for config/themen.json, clusters by version, a comparison of the apps, reply drafts for open 1–2 star reviews and free-text questions. Plus a list of measures per app (owner, impact, share of affected negative reviews), the most requested features and an effect check per update. There is no separate AI tab: each AI text sits in the section that answers the question (overview “What we should do” and “What do users say?”, Reviews tab, “Topics and words”, “Support replies”, “Apps compared”, “What an update changed”); only “Questions to the data” has its own tab “AI questions”.

Enabling: copy the ai block from config.example.json into config/config.json. The AI is active only if a provider in ai.providers has "enabled": true and the environment variable named in apiKeyEnvironmentVariable contains a key (for example export ANTHROPIC_API_KEY=…). If several are enabled, the first in the list wins; to switch, change the order or enabled. Providers: openai, gemini, anthropic, perplexity, xai (cloud) or local (a local model on your own computer, no key, free of charge, e.g. Ollama or LM Studio; for Ollama install it, ollama pull llama3.1:8b, enable the provider; setup and model choice in KI.md); the model per provider is free to choose (model). Without an active provider there is neither the command nor any AI content in the report.

Cost: only new or changed reviews are sent. monthlyTokenLimit is a hard brake per calendar month; ./ratings.sh ai-usage shows the usage. Free-text questions (ai.features.questions) are off by default because each question costs one request. Prices are listed by the provider; the tool stores none.

Privacy: review text and title (can be switched off: sendReviewText: false), stars, date, app version, language, country and app name are sent; never user names, review IDs, credentials or store figures. Every AI statement carries the “AI” mark and names provider, model and date. Quotes are checked against the original text; reply drafts are never sent, only shown for copying. Details in the privacy policy, section 4a.

Asking right in the report: ./ratings.sh ai-report does it all in one step: start the service, build the report, open the browser. Underneath, ./ratings.sh ai-serve starts a small service reachable only on this computer (127.0.0.1). If the report is generated while it runs, an input field appears on the “AI questions” tab, next to it “Choose a question …” with 20 ready-made questions from config/fragen.json (editable; one click asks at once); the report may then address exactly this port, otherwise it makes no network requests at all. Protection: random token per start, allowed browser origins only, requests capped at 4 KB, the same budget as elsewhere. Ctrl+C stops the service; the report published on the server cannot ask questions.

./ratings.sh analyze                   # all apps, only new items are sent
./ratings.sh analyze --dry-run         # only shows what would be sent
./ratings.sh ask "Which apps mention the bonus programme?" --customer kasse-nord

In the report: every AI text carries the “KI” mark. They appear in the overview (“What we should do”, “What do users say?”), in the reviews (sentiment strip, tiles, three buttons under “Topics and words”, reply drafts), in “Apps compared” and “What an update changed”, and on the “AI questions” tab. Printouts contain them only with AI enabled; the full report asks first whether to include the stored AI questions. Competitors (optional, Apple only)

Third-party Apple apps can be evaluated next to your own, without credentials: the tool reads Apple’s public review feed (newest 500 reviews per country) and the iTunes Lookup (store rating, total ratings, version). Google has no public route.

  • Setting up: in config/config.json the competitors block per customer (template in config.example.json): per entry id, name, optional vendor, plus apple.appId from the App Store link and the countries. Without entries nothing in the report changes.
  • Fetching: ./ratings.sh competitors, included in all and daily; menu: Fetch data → Competitors.
  • In the report: own tab “Competitors” with a table (vendor, store rating, total ratings, reviews of the last 90 days, traffic light by the same rules) and a profile per app; with AI, what users praise and criticise. The tab follows the customer in the filter. Competitors never count anywhere else: not in the overview, not in printouts, not in the notification.
  • Privacy: only review texts and figures from the public feed are stored, no user names; with AI these texts go to the provider as well.

Daily run, publishing, backup

  • Schedule: ./ratings.sh daily once a day (fetch, report, then the notification). cron: 30 6 * * * cd /home/ratings/app-ratings-reviews && ./ratings.sh daily >> logs-daily.txt 2>&1. Ready-made systemd units and the Mac, Windows and GitHub Actions variants are in BETRIEB.md.
  • Publishing: reports/ is static with no external dependencies. Serve it via a web server with a password or VPN, or put the folder on a network share (reportDirectory). Share only reports/, never config/, data/ or keys/.
  • Sending: ./ratings.sh markdown creates a 14-day summary per app and a ZIP.
  • Backup: ./ratings.sh backup packs data/; also include config/ and keys/ in the server backup.
  • Responsibility: someone checks the log when a status says “failed”; usually a key was revoked or expired.

Notification (optional)

So nobody has to open the report every day: at the end of ./ratings.sh daily the tool sends a short message via e-mail, Slack or webhook, but only when something happened since the last message. Nothing new, no message.

  • Triggers: new reviews with one or two stars (with the AI’s one-line summary if the analysis runs), a status change of an app (yellow, red or back to green, with the reasons as in the report), a jump in the crash rate. Each can be switched off (notify.triggers).
  • Enabling: block notify in config/config.json (template in config.example.json), enabled: true and the same on the channel; settings.reportUrl provides the link in the message. Password, webhook address and signing secret only as environment variables of the scheduler, never in the file.
  • Channels: e-mail via SMTP (STARTTLS or SSL), Slack incoming webhook, generic webhook (JSON via POST, optionally signed with X-Ratings-Signature). All enabled channels are served.
  • Behaviour: the first run reports nothing, it only remembers the state (data/notify-state.json). Every incident is reported once, even if daily runs several times. If no channel could deliver, the next run reports the same incidents again.
  • Checking: ./ratings.sh notify --test sends a test message to all channels; ./ratings.sh notify --dry-run shows what the next run would report. Both also in the menu under “Status and overview”.
  • Privacy: the message contains review excerpts (stars, date, country, title, shortened text); recipients belong to the company. User names never appear. No new AI request is made for the AI lines. Everything else is in BENACHRICHTIGUNG.md.
